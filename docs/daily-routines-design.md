# 자동 루틴 3종 설계 — 버그 스캔 · 계약 드리프트 · 아침 브리핑

작성일: 2026-07-21

## 1. 배경

ARC의 코드 리뷰는 현재 **PR 시점 Codex 리뷰**와 **주간 릴리스 게이트**가 담당한다.
이 구조가 놓치는 것이 두 가지 있다.

1. **잠복 버그** — 이미 머지된 코드에 남아 아무도 다시 보지 않는 결함.
2. **백엔드 계약 드리프트** — 프론트가 실재하지 않는 백엔드 계약을 가정하는 문제.
   FRT-116/117·FRT-120·FRT-123에서 **다섯 번 반복**됐고, 매번 화면이 조용히 오작동한 뒤에야 발견됐다.

두 번째가 특히 중요하다. 이 계열 결함은 **프론트 코드만 읽어서는 잡히지 않는다.**
문법적으로 멀쩡하고, 버그인 이유가 "백엔드에 그 계약이 없어서"이기 때문이다.
따라서 일반적인 버그 스캔이 아니라 **양쪽을 대조하는 별도 검사**가 필요하다.

여기에 더해, 매일 아침 "오늘 뭘 해야 하는가"를 한 번에 보여주는 브리핑을 만든다.

## 2. 목표 / 비목표

### 목표

- 우리가 발견하지 못하는 버그를 **매일** 찾아 Linear에 쌓는다.
- 백엔드 계약 불일치를 **화면이 깨지기 전에** 주간으로 잡는다.
- 매일 아침 **다음 행동이 보이는** 브리핑을 개인 Slack DM으로 받는다.
- 다음 회의까지 준비할 것을 **근거와 함께** 제시한다.

### 비목표

- **자동 수정 없음.** 세 루틴 모두 발견·보고만 한다. 코드 변경은 사람이 판단한다.
- 상황판(dashboard) 만들기. 브리핑은 읽고 넘기는 요약이 아니라 행동 목록이다.
- 기존 PR 시점 Codex 리뷰의 대체. 이 루틴들은 **보완재**다.

## 3. 배관 검증 결과 (2026-07-21 실측)

설계 전에 런타임 의존성을 실제로 호출해 확인했다. 추정이 아니라 실측값이다.

| 의존성 | 헤드리스 로컬 (`claude -p`) | 근거 |
|---|---|---|
| notion-arc MCP | ✅ 작동 | 회의록 DB 조회 → `[2026.07.19.] 22차 회의` 반환 |
| linear-arc MCP | ✅ 작동 | `linear_get_teams` → `Backend, Frontend` 반환 |
| Slack 채널 발송 | ✅ 가능 | `chat:write` 보유, `auth.test` ok (team `Arc`) |
| Slack DM 발송 | ❌ 불가 | `conversations.open` → `missing_scope` (`im:write` 필요) |
| Slack 채널 읽기 | ❌ 불가 | `conversations.history` → `missing_scope` (`channels:history` 필요) |
| CronCreate | ❌ 부적격 | **세션 전용**(in-memory, 세션 종료 시 소멸, 7일 자동 만료) |

### 이 결과가 뒤집은 것

- **CronCreate로는 매일 도는 루틴을 만들 수 없다.** launchd가 필요하다.
- **클라우드 루틴의 MCP 가용성은 미검증으로 남았다.** 반면 로컬은 실증됐다.
  기존 주간 릴리스 루틴이 클라우드에서 GitHub MCP를 쓰는 선례는 있으나,
  Notion·Linear MCP까지 붙는지는 확인되지 않았다.
  → **로컬을 런타임으로 택한다.** 검증된 환경을 쓰는 것이 새 배관을 뚫는 것보다 낫다.

## 4. 런타임

**macOS launchd → `claude -p` 헤드리스 실행 (로컬 맥)**

- launchd가 매일 새 `claude` 프로세스를 띄우므로 **Claude Code 세션에 묶이지 않는다.**
- 맥이 잠들어 있던 시간대의 작업은 `StartCalendarInterval` 규약에 따라 **깨어날 때 이어받는다.**
- 구독을 사용하므로 별도 API 키·과금이 필요 없다.

### 보안: 전권 금지

검증은 `--permission-mode bypassPermissions`로 했지만, **실제 루틴은 `--allowedTools` 화이트리스트로 묶는다.**
매일 무인으로 도는 프로세스에 전권을 주지 않는다.

- 허용: 파일 읽기·검색, git 읽기 명령, Notion/Linear/GitHub 조회, Linear 이슈 생성, Slack 발송
- 차단: 파일 쓰기·삭제, `git push`, `gh pr merge`, 임의 셸 실행

루틴은 **읽고 · 적고 · 알리기**만 할 수 있어야 한다. 코드를 건드릴 수단 자체를 주지 않는다.

### 식별정보는 리포 밖

release-gate가 팀 식별정보를 `RELEASE_GATE_CONFIG` 시크릿으로 뺀 선례를 따른다.
Slack 사용자 ID·채널 ID·Notion DB ID 등은 **`~/.arc/daily-routines.json`(리포 밖)** 에 두고,
리포에는 필드 이름만 문서화한다.

```jsonc
// ~/.arc/daily-routines.json  (chmod 600, 커밋 금지)
{
  "slackUserId":     "U…",        // 브리핑 DM 수신자
  "slackReadChannels": ["C…"],    // [요청] 스캔 대상 채널
  "notionMeetingDb": "…",         // 회의록 data_source_id
  "notionTaskDb":    "…",         // 태스크표 data_source_id
  "notionAssignee":  "…",         // 태스크표에서 '나'로 볼 Notion user id
  "linearTeam":      "Frontend"
}
```

## 5. 아키텍처 — 루틴 3개, 핸드오프는 Linear

```
05:07  daily-bug-scan        (저렴 모델)  ──생성──> Linear (Triage, label:bug-scan)
06:07  weekly-contract-drift (월요일만)   ──생성──> Linear (Triage, label:contract-drift)
08:07  daily-briefing        (일반 모델)  ──조회──> Linear + GitHub + Notion + Slack
                                            └──DM──> 개인 Slack
```

> 분(minute)을 `:00`이 아니라 `:07`로 두는 것은 의도적이다. 정각은 전 세계 스케줄러가 몰리는 시각이다.

### 핵심 결정: 루틴 간 통신 채널을 Linear 하나로 통일

스캔이 찾은 것을 브리핑에 넘기기 위해 **중간 상태 파일을 두지 않는다.**
스캔은 Linear에 적고, 브리핑은 Linear를 읽는다.

- 어차피 Linear 이슈는 만들기로 했으므로 **핸드오프가 공짜로 따라온다.**
- 중간 상태가 없으므로 **깨질 지점이 없다.** 한 루틴이 실패해도 다른 루틴이 오염되지 않는다.
- 사람이 Linear에서 이슈를 닫으면 그것이 곧 dedup 기록이 된다 (§6).

## 6. daily-bug-scan (매일 05:07, 저렴 모델)

### 대상 범위

매 실행마다 두 갈래를 함께 스캔한다.

1. **변경분** — 마지막 스캔 이후 `dev`에 들어온 diff. 항상 포함.
2. **전체의 1/7 슬라이스** — 소스 파일을 경로 정렬한 뒤 `index % 7 == 요일`인 것만.
   결정적 분할이므로 **7일이면 전체를 정확히 한 바퀴** 돈다.

"매일 전체를 조금씩" 훑는 형태다. 하루치 비용은 작게 유지하면서 커버리지는 주 단위로 100%가 된다.

### dedup — 이 루틴의 생사

dedup이 없으면 매일 같은 지적을 Linear에 재생성하고, 사흘이면 팀이 알림을 끈다.
**dedup은 부가 기능이 아니라 이 루틴이 살아남는 조건이다.**

**지문(fingerprint)** = `hash(파일경로 + 심볼/영역 + 카테고리)`

- **줄 번호를 쓰지 않는다.** 줄은 커밋마다 밀리므로, 포함하면 같은 버그가 매일 새 지문을 얻는다.
- 이슈 본문에 `<!-- scan-fp: … -->` 마커로 각인한다.

**대조 방법** — Linear 검색어에 의존하지 않는다.

1. `bug-scan` 라벨이 붙은 이슈를 **상태 무관(열림·완료·취소 전부)** 으로 전량 조회
2. 각 본문에서 `scan-fp` 마커 수집
3. 오늘 발견의 지문이 그 집합에 있으면 **건너뛴다**

취소(won't fix)로 닫은 것도 지문이 남아 다시 올라오지 않는다.
검색 인덱스 품질에 기대지 않으므로 결정적이다.

**영구 무시 목록** — `.claude/bug-scan-ignore.json`
스캔이 끈질기게 재보고하는 오탐을 손으로 박아 넣는다. 지문 또는 경로 glob을 받는다.

### 홍수 방지

첫 실행은 수십 건이 나올 것이 확실하다. Triage에 30건이 쏟아지면 그 자체가 노이즈다.

- **하루 최대 5건**만 등록한다 (심각도 상위).
- **잘라낸 건수를 브리핑에 반드시 명시한다.** 조용한 truncation은 "전부 훑었다"는 오해를 만든다.

## 7. weekly-contract-drift (월요일 06:07)

프론트의 API 호출·타입을 **백엔드 라이브 계약**과 대조한다.

- 출처: `api.story-arc.org/docs` + `gh api …?ref=dev` **원격 직독**
- **로컬 `arc-backend` 체크아웃은 신뢰하지 않는다.** FRT-116/117에서 낡은 로컬 사본을 근거로
  오판한 전례가 있다. 계약은 항상 원격에서 읽는다.

검사 항목:

- 프론트가 호출하는데 백엔드에 **없는** 엔드포인트 (팬텀)
- 응답 필드 이름·형태 불일치 (snake/camel, 중첩 래핑)
- 프론트 타입이 가정하는 필드 중 백엔드가 **주지 않는** 것

발견은 `contract-drift` 라벨로 Linear에 등록하고, 요약은 월요일 브리핑에 싣는다.
dedup은 §6과 동일한 지문 방식을 공유한다.

## 8. daily-briefing (매일 08:07, 개인 Slack DM)

주말 포함 **매일** 발송한다.

### 매일 싣는 것

1. 밤사이 신규 버그 N건 (Linear 링크) + **잘라낸 건수**
2. 열린 PR의 CI 상태 — **실패한 것 강조**
3. 내 응답을 기다리는 리뷰 코멘트 (미해결 Codex P2 등)
4. 마감 임박 Linear 이슈
5. **다음 회의 준비물** (아래 §8.1)

### 월요일에 추가로 싣는 것

6. `dev`↔`main` 미배포 잔량 (릴리스 게이트 상태)
7. 계약 드리프트 주간 결과

6·7을 매일 싣지 않는 이유: 릴리스 상태는 이미 주간 게이트가 Slack으로 알리고,
계약 드리프트는 주 1회만 갱신된다. 매일 실으면 브리핑만 무거워진다.

### 8.1 다음 회의 준비물

**회의일 판정** — 회의록 DB는 회의 *전에* 페이지가 생성된다(22차 페이지는 7/15 생성, 회의는 7/19).
따라서 추측하지 않고 읽을 수 있다.

1. 회의록 DB에 **미래 날짜 페이지가 있으면 그것**이 권위 있는 답이다.
2. 없으면 **다음 수요일 또는 일요일**로 파생한다.
   실제 리듬이 수/일로 고정임을 확인했다 — 7/5(일)·7/8(수)·7/12(일)·7/15(수)·7/19(일).
3. **어느 쪽으로 판정했는지 브리핑에 표시한다.** ("회의록 등록됨" vs "수/일 규칙으로 추정")

**준비물 산출** — 두 갈래를 합친다.

| 갈래 | 출처 | 신뢰도 |
|---|---|---|
| 구조화 | 태스크표: `담당자=나` & `마감기한 ≤ 회의일` & 상태 미완료 | 확실 |
| 추론 | 최근 회의록 본문 · Slack `[요청]` 메시지 | 검증 필요 |

### 8.2 환각 방지 규칙 (하드 룰)

추론 갈래는 값어치가 크지만 **ARC가 이미 다섯 번 데인 "계약 오가정" 패턴을 브리핑에서 반복할 위험**이 있다.
따라서 구조적으로 막는다.

> **추론 항목은 근거 링크를 반드시 동반한다.
> 근거를 제시할 수 없으면 그 항목을 출력하지 않는다.**

```
- 키워드 v4.1 명세 백엔드 배포 여부 확인   (근거: 22차 회의록 › 3번째 항목)
- 결제 PG 심사 리드타임 공유                (근거: #p-admin-page 7/20 메시지)
```

링크가 붙으면 사용자가 30초 안에 검증할 수 있다. 링크를 못 다는 항목은 애초에 신뢰할 수 없는 항목이다.

## 9. 로직은 레포에, 루틴은 포인터

launchd plist나 루틴 프롬프트에 로직을 직접 박으면 수정 이력이 남지 않는다.

- 실제 지침은 **`.claude/routines/*.md`로 커밋**한다
  (`daily-bug-scan.md` · `weekly-contract-drift.md` · `daily-briefing.md`)
- launchd가 호출하는 프롬프트는 **"이 파일을 읽고 따르라" 한 줄**만 둔다

브리핑·스캔은 반드시 여러 번 튜닝하게 되는 물건이다. 튜닝이 PR로 남아 리뷰 가능해야 한다.

## 10. 미해결 · 리스크

### 착수 전 해소 필요

- **Slack 스코프** — 2026-07-21 재확인 시점에도 `im:write`·`channels:history`가 **여전히 없다.**
  앱 설정에 스코프를 추가한 뒤 **Reinstall to Workspace를 완료**해야 토큰에 반영된다.
  재발급된 토큰은 `~/.arc/slack-bot-token`에도 갱신해야 한다.
  - 미해소 시 영향: 브리핑을 DM으로 못 보냄(채널 발송으로 대체 가능),
    `[요청]` 메시지 읽기 조각 누락. **나머지 기능은 정상 동작한다.**

- **Linear 조회 경로** — `linear_search_issues`의 `query` 파라미터가 서버 내부에서 깨져 있다
  (GraphQL `IssueFilter.search` 필드 부재 → `-32603`).
  dedup이 "라벨로 이슈 전량 조회"에 의존하므로 **작동하는 조회 경로를 구현 1순위로 확정**해야 한다.
  안 되면 Linear GraphQL 직접 호출로 우회한다.

### 남는 리스크

- **맥 의존** — 맥이 장기간 꺼져 있으면 루틴이 밀린다. 상시 가동 전제가 깨지면 재검토한다.
- **저렴 모델의 오탐** — Triage에 쌓이는 것이 전제이므로 사람이 버리면 그만이지만,
  오탐 비율이 높으면 ignore-list 관리 부담이 커진다. 2주 운영 후 재평가한다.
- **브리핑 유용성** — 무엇이 유용한지는 굴려봐야 안다.
  그래서 팀 채널이 아니라 **개인 DM으로 시작**한다. 다듬은 뒤 공유 범위를 넓힌다.

## 11. 구현 순서

1. **Linear 조회 경로 확정** — dedup의 전제. 여기서 막히면 나머지가 헛돈다.
2. **daily-bug-scan** — 지문·ignore-list·상한 포함. 수동 1회 실행으로 검증.
3. **daily-briefing** (5번 항목 제외) — Linear/GitHub 조회 → DM 발송까지 연결.
4. **회의 준비물(§8.1)** 추가 — Notion 태스크표 → 근거 링크 규칙.
5. **weekly-contract-drift** — 주간이므로 마지막.
6. **launchd 등록** — 각 루틴을 수동 검증한 *뒤에* 자동화한다.

각 단계는 launchd에 걸기 전에 **손으로 한 번 돌려 결과를 눈으로 확인**한다.
매일 무인으로 도는 물건을 검증 없이 스케줄에 올리지 않는다.
