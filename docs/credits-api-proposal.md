# BAC-38: 비용 비공개 크레딧 API 제안

상태: 프론트 제안, 백엔드 합의·구현 전. 2026-09-27 사용자 결정으로 기존 공개 비용 정책 계약을 대체한다.
관련: BAC-36/37/38/71/72, FRT-344/98/99/101.

## 목적과 이번 구현 범위

기능별 차감량은 랜딩뿐 아니라 생성 직전에도 공개하지 않는다. HTML, 브라우저 번들,
API 응답, 오류 상세, 분석 이벤트에도 비용표와 예상 생성 횟수를 보내지 않는다.
정확한 비용과 지급·예약·확정·해제 원장은 서버가 보관한다.

FRT-344에서는 기존 랜딩의 가입 지급 약속, 충전 패키지와 가격, 생성 횟수, 프론트 비용
상수를 제거한다. 기록·보관·개별 분석은 무료로 안내하고 나머지 기능의 크레딧 이용과
충전은 준비 중으로 구분한다. 랜딩은 정적 안내이므로 비용 정책 API를 호출하지 않는다.
이번 PR은 API 구현이나 실제 차감 활성화를 포함하지 않는다.

## 노출 경계

| 데이터 | 사용자 브라우저 | 권한 있는 서버·운영자 |
| --- | --- | --- |
| 기능별 사용 가능·부족·준비 중 상태 | 허용 | 허용 |
| 기능별 비용·정책 버전별 비용표 | 제외 | 허용 |
| 정확한 balance/reserved/available | 아래 제안대로 제외 | 필수 |
| 거래별 증감량·거래 후 잔액 | 제외 | 필수 |
| 본인의 이용 일시·기능·처리 상태 | 허용 | 허용 |
| 운영 메모·타인 정보 | 제외 | 별도 권한 |

**후속 화면에 대한 제안:** 정확한 잔액을 노출하면 생성 전후 차이로 비용을 알 수 있다.
전체 비공개 의도에 맞춰 FRT-98의 숫자 잔액은 상태 표시로, FRT-101의 숫자 거래 원장은
이용 내역으로 변경할 것을 제안한다. 이번에는 해당 화면을 수정하지 않는다.
사용 가능 여부를 반복 관찰하거나 미래의 충전량과 비교하여 비용을 추정할 가능성까지
없애는 보안 경계는 아니다. 여기서 보장하는 것은 정확한 비용의 직접 전송·표시 금지다.

## 인증된 GET /credits

기존 인증 쿠키를 사용하며 본인 정보만 응답한다. envelope 없이 아래 객체를 반환하는 안이다.

```json
{
  "revision": "opaque-account-revision",
  "as_of": "2026-09-27T00:00:00Z",
  "billing_status": "preparing",
  "top_up_status": "unavailable",
  "features": {
    "comprehensive": { "status": "preparing" },
    "keyword": { "status": "preparing" },
    "resume": { "status": "preparing" },
    "cover_letter": { "status": "preparing" }
  }
}
```

- `billing_status`: `preparing | active`. 아직 적용되지 않은 과금을 활성 상태로 가장하지 않는다.
- `top_up_status`: 현재 `unavailable`만 지원. 결제 후속 계약이 확정되기 전 구매 버튼을 만들지 않는다.
- 각 `status`: `available | insufficient | preparing | temporarily_unavailable`.
- 개별 분석은 크레딧 조회·예약에서 제외한다. 네 기능 ID는 구분한다.
- `revision`은 비용을 인코딩하지 않는 불투명 변경 토큰이다. 차감 권한이나 견적 보장이 아니다.
- `Cache-Control: private, no-store`. CDN·정적 캐시 및 localStorage에 개인 상태를 저장하지 않는다.
- 화면 진입·다시 포커스·생성 접수·완료·실패 후 재조회한다. 응답 순서 경합은 최신 요청만 반영한다.
- 네 기능 누락이나 알 수 없는 상태는 클라이언트에서 확인 실패로 취급한다. 무료·잔액 0·사용 가능으로 추정하지 않는다.
- 조회 오류는 “이용 가능 여부를 확인하지 못했어요”와 재시도 안내로 표현한다. 기존 입력은 보존한다.
- `preparing`은 크레딧 제도 미활성 상태다. 기존 비과금 생성 흐름을 이 값 때문에 차단하지 않는다.
  `active` 환경에서의 로딩·확인 실패·부족 처리 구현은 FRT-99 범위다.

공개 `GET /credits/policy`는 제공하지 않는다. 인증된 `/credits`에도 비용표를 포함하지 않는다.
서버 정책 변경은 다음 조회와 실제 생성 요청에 즉시 반영된다. 비용이 바뀌어도 랜딩 문구는 바뀔 필요가 없다.
제도 활성화·충전 출시처럼 제공 범위가 바뀔 때는 랜딩 문구를 별도 배포로 갱신한다.

## 생성 요청과 부족 응답

기존 네 생성 엔드포인트를 유지한다. 클라이언트는 비용·잔액·정책 버전을 제출하지 않는다.
서버가 요청 시 현재 정책과 실제 가용 잔액을 원자적으로 검사하고 예약한다.
사전 조회에서 `available`이었어도 동시 요청 때문에 생성 요청은 거절될 수 있다.
응답 유실 재요청은 동일한 멱등 키로 같은 논리 작업을 반환한다(BAC-71 계약).

```json
{
  "code": "INSUFFICIENT_CREDITS",
  "message": "이 기능을 이용할 크레딧이 부족해요."
}
```

HTTP 402. 기존 `normalizeErrorBody`가 읽는 최상위 `code`/`message` 형식을 사용한다.
`required`, `balance`, `available`, `shortfall`, 비용표 등 숫자는 포함하지 않는다.
프론트는 입력을 유지하고 상태를 재조회한다. 충전 미제공 상태에서는 충전 CTA를 표시하지 않는다.
401은 기존 인증 처리, 403은 권한 오류, 5xx/네트워크 오류는 일시 오류로 구분한다.
예약·정산 서비스 장애를 부족(402)으로 위장하지 않는다.

예약, 결과 저장과 확정의 원자성, 실패 시 해제, 중복 콜백·재시도 처리는 BAC-36/37/71이 담당한다.
사용자 응답·작업 조회·다운로드 메타데이터에 내부 비용을 재노출하지 않는다.

## 인증된 GET /credits/transactions

사용자용 이용 내역 projection을 제공한다. 원장 행을 그대로 직렬화하지 않는다.

```json
{
  "items": [
    {
      "id": "usage-event-id",
      "kind": "usage",
      "feature": "resume",
      "status": "completed",
      "occurred_at": "2026-09-27T00:00:00Z"
    }
  ],
  "next_cursor": null
}
```

- `kind`: `usage | grant | adjustment`. 비사용 항목의 `feature`는 `null`.
- `status`: `processing | completed | failed`. 실패를 확정 차감으로 표시하지 않는다.
- 예약·확정·해제를 각각 중복 표시하지 않고 논리 작업당 한 항목을 갱신한다.
- `cursor`는 불투명 토큰, `limit` 기본 20/최대 100. 첫 페이지 스냅샷과 `(occurred_at DESC, id DESC)` 정렬을
  커서에 고정하여 후속 페이지의 삽입으로 중복·누락되지 않게 한다. 재조회 시 새 스냅샷을 시작한다.
- 인증 본인만, `private, no-store`. 운영자·사유 자유문·금액·거래 후 잔액은 제외한다.
- 운영용 정확한 원장 및 대사는 BAC-72의 별도 권한 경로에 남긴다.

## 적용 순서와 검증 기준

1. FRT-344: 정적 랜딩 정리 및 기존 클라이언트 비용 상수 제거. 모바일·데스크톱과 가입 링크 확인.
2. BAC-38: 이 제안을 검토하여 필드·오류·캐시 계약 확정. 서버 비용표는 내부 config로 유지.
3. FRT-98/101/99: 상태 조회·이용 내역·실행 게이트를 확정 계약으로 구현. mock은 실제 제공 상태가 아니다.
4. 서버 통합 후 실제 지급→예약→성공/실패·동시 요청·정책 변경을 검증한다.

후속 계약 테스트는 비용·잔액·증감량 필드가 모든 사용자 응답(402 포함)에 없는지,
타인 내역 접근 거부, 조회 장애와 부족 상태 구분, 입력 보존, 두 탭의 사전 조회 이후 경쟁,
정책 변경 후 다음 요청의 서버 재검증을 포함한다. 브라우저 번들·HTML·분석 이벤트에도 비용을 넣지 않는다.

패키지 가격, 가입 지급량, 실결제·미션·Fake door는 여기서 확정하거나 구현하지 않는다.
