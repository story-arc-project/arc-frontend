# 종합 분석 요청 키 (FRT-361)

`POST /analysis/comprehensive`는 `Idempotency-Key`를 요구한다. 키는 HTTP 전송 횟수가 아니라 사용자가 시작한 논리 요청을 식별한다.

- 새 종합 분석 요청은 UUID 키와 선택한 경험 ID의 스냅샷을 함께 사용한다.
- 같은 화면에서 응답 유실, 네트워크 오류, 5xx, 성공 응답 본문 파싱 실패 뒤 재전송할 때는 같은 키를 유지한다. 인증 갱신 후 API client의 내부 재전송도 같은 헤더를 유지한다.
- 처리 중일 수 있는 409에 새 키를 자동 발급하지 않는다. 입력 변경, 계정 변경, 명확한 요청 거절 뒤 새 실행은 별도 요청으로 구분한다.
- 키는 화면 메모리에만 보관한다. 새로고침·다른 화면으로 이동 후 복귀·다른 탭 사이의 중복 요청 복구는 보장하지 않는다. 요청을 받았는지 불확실할 때는 분석 목록을 확인해야 한다.
- 키나 사용자 입력을 analytics 또는 브라우저 영구 저장소에 추가로 기록하지 않는다. 잔액을 클라이언트에서 차감하지 않는다.

## 서버와의 연결 범위

검토 기준은 backend `02f01a5`, frontend `e4fde4e`다. 백엔드 CORS 설정은 `allow_headers=["*"]`이지만 실제 배포의 preflight 응답은 별도 확인이 필요하다.

이번 수정은 새 종합 분석 요청의 헤더 호환성과 프론트 재전송 키 관리다. 서버의 사용자·payload 검증, 동시 요청 직렬화, RELEASED 예약 처리 및 실제 차감의 완성을 의미하지 않는다.

- [BAC-87](https://linear.app/story-arc/issue/BAC-87): 실패한 분석의 `/retry` 계약과 예약 재생성. 서버 계약 확정 전에는 이 경로를 변경하지 않는다.
- [BAC-88](https://linear.app/story-arc/issue/BAC-88): 성공 시 capture, 비동기 최종 실패 시 release.
- [BAC-71](https://linear.app/story-arc/issue/BAC-71): 사용자·요청 payload 검증, 중복·역순 콜백, 예약 복구 등 전체 정산 연결.

실패 응답의 상태·코드는 API에서 그대로 전달한다. 부족 안내와 서버 커밋 이후 잔액 재조회는 FRT-99에서 연결한다.

## 확인 방법

유닛 테스트는 필수 헤더, 오류 보존, 같은 요청 재전송, 입력·계정 변경, 중복 클릭을 검증한다. `e2e/comprehensive-idempotency.spec.ts`는 실제 브라우저에서 네트워크 실패·503 뒤 동일 키와 402 뒤 새 키를 확인한다. 브라우저 테스트의 API는 스텁이며 운영 서버의 멱등성·과금 검증을 대신하지 않는다.
