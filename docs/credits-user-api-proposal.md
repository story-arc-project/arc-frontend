# BAC-38: 로그인 사용자 잔액 조회 API 제안

상태: 2026-09-30 프론트 구현을 위한 제안. 백엔드 합의·구현·실제 정산 연동은 미검증.
관련: FRT-98, BAC-38, BAC-36/37/71. 공개 상품 계약은 [패키지 API](./credits-api-proposal.md).

## 확정된 제품 범위

로그인한 사용자는 **자기 잔액을 정확한 숫자로 확인한다**. 랜딩에서 개인 잔액을 숨긴다는
정책을 인증 사용자 화면까지 확대하지 않는다. 주 표시는 사용 가능한 `available`이며
`reserved`는 필요할 때 '처리 중'으로 별도 표시한다. 기능별 비용표와 거래별 차감량의
표시 정책은 이번 잔액 계약과 별개다. 공개 패키지 이름·수량·가격은 기존 계약을 유지한다.

## GET /credits

기존 인증 쿠키로 본인 계정을 판별한다. 요청에 사용자 ID를 받지 않는다.

```json
{
  "balance": 50,
  "reserved": 3,
  "available": 47,
  "updated_at": "2026-09-30T00:00:00Z"
}
```

| 필드 | 의미 |
| --- | --- |
| balance | 확정된 지급·차감·보정 원장의 합계 |
| reserved | 진행 중인 활성 예약의 합계 |
| available | 지금 사용할 수 있는 잔액. balance - reserved |
| updated_at | 예약을 포함한 계정 상태의 마지막 변경 시각. timezone을 포함하는 유효한 ISO timestamp |

- 수치는 0 이상의 JavaScript safe integer다. `reserved <= balance`, `available === balance - reserved`를 보장한다.
- 세 수치와 시각은 같은 일관된 스냅샷에서 읽는다. 숫자 문자열·소수·누락·음수·불일치 응답은 프론트에서 오류로 처리한다.
- 0은 유효한 성공 응답이다. 가입 지급량이나 임의 잔액을 fallback으로 만들지 않는다.
- 정의된 필드만 채택하며 알 수 없는 필드는 버린다. 내부 메모·비용표·원장·타 사용자 정보는 제외한다.
- 브라우저 `cache: no-store`; 서버 `Cache-Control: private, no-store` 제안. 공개 CDN 캐시를 사용하지 않는다.
- 기존 API origin에 인증 쿠키를 전송한다. cross-origin이면 credentials 허용 및 정확한 origin CORS가 필요하다.

## 오류와 인증

| 상황 | 프론트 처리 |
| --- | --- |
| 정상 200 + 유효한 잔액 | 성공, 정확한 서버 잔액 사용 |
| 404 / 501 | API 미제공 상태. 잔액 0이나 부족으로 해석하지 않음 |
| 401 / 403 | 기존 인증 클라이언트의 갱신·재인증·권한 오류 규칙 적용 |
| 5xx / 네트워크 / JSON·계약 오류 | 조회 오류 및 수동 재시도 |
| 기존 잔액이 있는 상태에서 재조회 실패 | 같은 계정의 마지막 값은 stale로 유지; 최신 상태라고 표시하지 않음 |

예외는 HTTP 상태와 `code`/`message`로 구분한다. 조회 실패를 `INSUFFICIENT_CREDITS`로 변환하지 않는다.
프론트의 전체 조회 대기는 인증 재시도·응답 본문 처리를 포함해 10초로 제한한다. 초과하면 요청을 취소하고 조회 오류로 처리하며 재시도할 수 있다.
404/501은 계정 미생성·잔액 없음 표현에 사용하지 않는다. 정상 계정의 실제 0 잔액은 200으로 반환한다.

## 프론트 공유 상태와 갱신

`CreditsProvider` + `useCredits()`를 여러 화면에서 공유한다. 새로운 캐시 라이브러리는 추가하지 않는다.
상태는 idle/loading/success/error/unavailable, data/error, isRefreshing/isStale, refetch로 구성한다.
Provider를 main 레이아웃에 두되 소비자가 있을 때만 조회한다. 현재 화면에 배지를 추가하거나 설정 카드를 바꾸지 않는다.

- 인증 확인 전·로그아웃에는 조회하지 않는다. 계정 변경 시 이전 값·진행 요청을 폐기한다.
- 메모리에서만 유지한다. localStorage나 분석 이벤트에 잔액·계정 식별자를 저장하지 않는다.
- 동시에 여러 화면이 요청하면 하나의 조회를 공유한다. 이전 계정의 늦은 응답은 무시한다.
- 탭 복귀·온라인 복귀·수동 재조회와 명시적인 무효화 신호에 갱신한다.
- 요청 중 무효화되면 이후 재조회를 예약한다. 변경 전 시작한 요청만으로 변경 후 상태를 확정하지 않는다.
- 서버값을 직접 더하거나 빼지 않는다. 클라이언트 잔액으로 실행 승인을 보장하지 않는다.

## 작업 연동 지점과 서버 반영 시점

후속 작업은 성공적으로 예약·지급·확정·해제가 서버에 반영된 이후 `invalidateCredits()`를 호출한다.
화면 안에서는 `useCredits().refetch()`도 가능하다. 단순 요청 접수·타이머 완료·analytics 이벤트를
정산 완료로 간주하지 않는다. 아래의 실제 연결은 BAC-71/FRT-99 및 각 작업 흐름에서 검증한다.

| 사건 | 후속 연결 지점 | 서버 완료 기준 |
| --- | --- | --- |
| 종합/키워드 분석·이력서/자기소개서 요청 수락 | 해당 create API 성공 처리 | 예약 트랜잭션 커밋 후 응답 |
| 생성 완료 | 기존 작업 폴링의 완료 전환 | 결과 저장 + capture 커밋 후 완료 상태 노출 |
| 실패·취소·타임아웃 | 기존 작업 상태의 실패 전환 | release 커밋 후 종료 상태 노출 |
| 운영 지급 | 지급 확인 후 수동/포커스 재조회 | 지급 원장 커밋 후 성공 응답 |

처리 중 작업이 있어도 읽기 요청 자체는 예약·차감을 만들지 않는다. 개별 분석의 무료 경로는 유지한다.
현재 작업에서 모든 생성 흐름에 bridge를 연결하거나 실제 정산 검증을 완료했다고 주장하지 않는다.

## 완료 기준

이번 프론트 기반: 방어 파싱, 공유 조회, 사용자 전환, 중복 조회, 무효화 중 경합, 오류·stale 구분,
main 레이아웃 회귀와 lint/typecheck/unit/build를 검증한다. 테스트 mock은 실제 사용자 잔액으로 배포하지 않는다.

통합 완료(백엔드 후속): 인증 본인만 조회, 지급/예약/capture/release 수치 정합, 개별 분석 불변,
운영 지급 후 갱신, 실제 작업 상태와 정산 타이밍을 검증한다. 이때까지 FRT-98을 전체 Done으로 처리하지 않는다.

FRT-101은 설정 카드·내역 화면, FRT-99는 부족 안내·입력 보존·서버 실행 거절 처리를 맡는다.
결제/PG·Fake door·미션·추천인은 이번 범위에 포함하지 않는다.
